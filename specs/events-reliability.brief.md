# MCP Events 缺陷修复简报

范围：MCP 互操作与事件交付。以下三项在同一次改动中修复。

## 目标

工程师订阅 Bugzilla 工单变化后，ChatGPT 能收到符合条件的事件并完成一次只读初诊。工程师可以打开原工单复核。扫描未完成、历史不可重放和权限撤销都不能被当作没有新事件。

## 依据

- [项目目标](brief.md)保留纯 REST 采集，云端负责初诊，本地看板负责人工复核。
- [项目行为契约](architecture-and-contracts.md)继续约束版本隔离、写入归因、游标和 Webhook 安全。本简报描述修复范围，不替代冻结契约。
- [ChatGPT Events 文档](https://developers.openai.com/plugins/build/mcp-events)定义两代 HTTP 的 Webhook 接入。依据工作区 2026-11-19 的存档。
- [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)定义独立的 Events 扩展。依据工作区存档的 PR 提交 `60b15c16`。

## 不在本次范围

- 不实现实时 SSE。[行为契约](architecture-and-contracts.md)第 3.4 节将 `events/stream` 留至后续交付，本次不声明 `push`。
- 不改 Bugzilla 源码，不要求安装 Perl 扩展，不引入外部消息队列。
- 不开放事件触发的自动写回。
- 不改本地看板、人工审批和普通工具调用的行为。

## 修复决定

### 1. 声明支持的订阅能送达

旧版 HTTP 声明了 Events，但 `events/list` 返回 `-32601`。`2025-11-25` 和 `2026-07-28` 的 ChatGPT 入口共用事件服务，各自保留版本协商、鉴权和报文校验。声明 `capabilities.events` 后，客户端必须能调用 `events/list`、`events/subscribe` 和 `events/unsubscribe`。

Webhook 部署同时接入出站发送器、持久存储和投递循环。启用时，缺少任一项都在启动时报错。未启用时，ChatGPT 不声明 `capabilities.events`，SEP-3415 的事件目录只列启用的方式。未启用的方式不能创建订阅。

验证回调、投递事件和发送控制消息都遵守 `R-28f5c2`。不要因为接入发送器而放宽 HTTPS、地址校验、固定拨号地址或禁止重定向的要求。

网络超时和可重试的 HTTP 响应都消耗重试预算。服务端持久保存已用次数和下次重试时间。重试前检查当前可见性，保留消息 ID，并使用新时间戳签名。收到 `410` 或 `413` 时不再重试该条投递。

客户端游标不能越过尚未解决的投递。无法补送时先持久记录缺口。SEP-3415 发送签名的 `gap`。ChatGPT 在订阅刷新时返回 `truncated: true`，不发送 `gap` 或 `terminated` 控制消息。

### 2. 只过滤能确认是本服务写入的事件

`includeSelf: false` 未过滤服务端自己创建的工单。写入端和采集端使用同一套记录标识。创建工单用 Bugzilla 返回的工单 ID，评论用评论 ID。字段更新用 Bugzilla 确认的变更与历史记录对账，不用请求差异的哈希代替上游记录。

没有唯一匹配时，照常交付符合条件的事件。不能凭账号、工单、同秒时间戳或评论文本猜测来源。首个闭环使用服务端限制的只读权限。写入归因、幂等和服务端因果写入预算通过验收后，再单独评估自动写回。

### 3. 过滤和扫描状态可信

目前 `severity: "critical"` 仍会收到 `normal` 工单。事件目录、请求校验和实际筛选使用同一组条件。服务端拒绝不支持的条件。创建事件的 `severity` 按扫描时 Bugzilla 返回的值筛选，不把它当作历史快照。

完整扫描没有匹配项时，`events/poll` 可以返回空批次并推进游标。扫描未完成时，保留原游标，并返回可区分的失败响应。Webhook 使用运维信号区分扫描延迟、正常空闲和权限撤销，不向 ChatGPT 发送额外的协议消息。只有无法重放的历史才标记 `truncated: true`。

## 验收条件

- **HTTP 声明和路由。** 两代 ChatGPT HTTP 会话均能列出事件、验证回调、接收事件，再取消订阅。无效的现代请求不降级到旧版。分别验证 Webhook 未启用、显式启用但依赖缺失和完整启用三种状态。未实现的 `push` 不出现在目录中，直接请求也不假装成功。
- **投递与恢复。** 让回调超时后重启服务。确认重试不重置预算或消息 ID，且不会早于退避期限发送。分别验证 `410`、`413`、预算耗尽和重试前撤权。确认两个配置各自报告缺口，不越过待投递事件。
- **写入归因。** 用 `includeSelf: false` 订阅，确认可信的本服务创建、评论和字段更新不会交付。用同一 Bugzilla 账号在同一秒提交不同的真人变更，确认真人事件仍可收到。给出不能唯一归因的历史记录，确认符合条件的事件仍交付，且初诊路径不能自动写回。
- **筛选和扫描。** `critical` 创建订阅接收 `critical` 工单，不接收 `normal` 工单。不支持的筛选参数应报错。上游分页中途失败时，客户端收到失败响应，游标不前移。恢复后用原游标收到符合条件的事件。完整扫描但无匹配项时，客户端收到空批次，游标只推进到已验证的位置。

对应的需求编号见[行为契约](architecture-and-contracts.md)第 4.2 至 4.4 节。从公开 HTTP、回调接收端和 Bugzilla 记录验证，不只检查内部计数。

## 人工复核

用现有 `bugIds` 在目标 ChatGPT 宿主订阅一张测试工单的新评论。由人在真实 Bugzilla 实例发表评论。确认宿主完成对应的只读初诊，且工程师能打开原工单复核。Webhook `2xx` 只证明回调已收件。

请工程师判断初诊是否足以开始复核，以及遇到授权失效或历史缺口时，是否知道要重新授权或到 Bugzilla 补查。
